# Automations

Use the typed authoring API. Discover CreateAutomationInput, UpdateAutomationInput, AutomationConfigInput and validateAutomation. Read the automation-config reference for their fields. Each node config is an object containing exactly one of trigger, condition, operator, action or macro. Hive compiles standard controls into validated runtime expressions. Prefer standard controls whenever they express the request. Custom expressions are for logic requiring them.

Resolve names against live rooms, groups, devices, scenes and effects. A room is an output target; a motion sensor is an input device. Inspect room membership and reported capabilities to identify its sensor. A sensor elsewhere in the home is not implicitly the room's sensor. If no unambiguous sensor is associated with the requested room, ask which device to use. Do not silently substitute the only motion sensor in the home.

Graph wiring carries activation signals. A condition requires an incoming connection from a trigger path. It evaluates only when a signal reaches it and forwards that signal only if its predicate passes. Chain multiple required guards: trigger → condition → condition → action. A condition's negate flag inverts its predicate; errors always block. AND passes only when every input passed in the current evaluation; OR passes when any input passed. Alternative conditions must each receive a trigger signal before their outputs feed OR. An action with multiple inputs also merges them as OR. Never bypass a required guard with a direct trigger-to-action connection.

For a motion-controlled night scene, create these two branches:

- `motion-on`: trigger mode `device_state`, deviceId of the chosen sensor, property `occupancy`, comparator `==`, value `{booleanValue:true}`. `night-hours`: condition mode `time_window`, afterHour 0, afterMinute 0, beforeHour 4, beforeMinute 0. Wire `motion-on` → `night-hours` → action `activate_scene`, payload `{sceneId:...}`.
- `motion-off`: trigger mode `device_state` on the same sensor, property `occupancy`, comparator `==`, value `{booleanValue:false}`, holdMs 600000. `night-active`: condition mode `custom`, customExpr `scene_active("SCENE_ID")`. Wire `motion-off` → `night-active` → action `set_device_state`, targetType `room`, targetId of the requested room, payload `{on:false}`.

The time window gates activation. The inactivity path still turns the lights off after 04:00. `holdMs` measures continuous absence, resets when occupancy becomes true, and fires once until the condition rearms. The scene-active check avoids turning off a different scene the user selected. Ask if the requested behavior differs. Times and schedules follow Hive's configured timezone.

Use typed literals: `{stringValue:"true"}` is different from `{booleanValue:true}`. Numbers use numberValue; an explicit null uses `{nullValue:true}`. Exactly one value field is allowed. State properties use camelCase (`colorTemp`, `targetTemperature`). Hold, grace and cooldown durations are milliseconds; expression `since()` returns seconds.

Other standard trigger modes are device_event (deviceId and optional eventValue), availability (deviceId), webhook (endpointId and typed filters), and schedule (scheduleSubmode at/every/custom). At schedules use hour/minute/second and weekday codes MON–SUN; every schedules use an interval value and seconds/minutes/hours. An empty weekday list means every day. Custom triggers require eventType and customExpr; a held custom device-state trigger also requires deviceId.

Condition modes are time_window, weekday, device_state (targetType device/room/group, targetId, property, comparator and typed value), and custom. Conditions support negate, default false. Operators use kind and/or. Actions include set_device_state, toggle_device_state, change_value, configure_device, activate_scene, cycle_scenes, run_effect, raise_alarm and clear_alarm. Discover the payload fields for the action, and supply only fields belonging to it. `activate_scene` uses payload.sceneId; `run_effect` uses payload.effectId or payload.nativeName. Device configuration uses a list of typed settings. Use selectors only when the user wants capability-based or structural targeting.

Preserve node IDs, positions, edges, definitions and unrelated configuration during edits. Omitted nodes/edges preserve the saved lists; supplied lists replace them completely. Named definitions and macro argument templates are JSON; macro nodes use `{macro:{name,arguments,negate}}`. Read an existing definition before calling or modifying it.

Call validateAutomation on the entire proposed graph before saving. Inspect every error and warning and fix unintended wiring. Validation checks structural and configuration validity, not whether the graph satisfies the user’s intent. Trace each action’s inputs: motion outside the time window must not activate the scene; absence while another scene is active must not switch it off. Save with the current expectedRevision, then re-read validation, nodes and edges. Enabled graphs must validate; disabled drafts may retain incomplete controls. Do not describe a draft as ready. Compilation and saving do not prove that the physical automation has fired. Only fire a trigger when the user requested an immediate run.
